## Context provenance
- `按我这个app的逻辑，搞一个artifact，每周更新` (current user request; establishes that the artifact must reproduce the user's existing app logic and refresh weekly)
- `"按我这个app的逻辑"指用户自研 Electron 应用 Firance（源码在用户 Mac，完整本地路径已省略，未记录），仪表盘必须 1:1 复刻其 Home 与 Dashboard 视图的计算口径。` (parent-agent clarification derived from the user's app investigation; defines the authoritative calculation and display model)

- Parent-agent supplied exact Firance formulas for monthly aggregation, contribution fallback, flexible spend, investment return, and FIRE metrics; these formulas will be implemented directly rather than reinterpreted.

## Tested sources
### Plaid linked financial data
**Used by**: `refreshFinanceData` background retrieval, live net-worth fusion, weekly comparison, holdings Top 10, account-detail refresh
**Test command**: `which plaid; plaid status | jq ...; plaid accounts | jq ...; plaid liabilities | jq ...; plaid investments-holdings | jq ...`
**Sample output**: Plaid is connected. The account read returned linked loan, depository, credit, brokerage, IRA, 401(k), HSA, and crypto accounts with masked suffixes and current balances. The liabilities read returned a mortgage at 2.375%. The holdings read returned 5 institutions and 72 holdings; a schema check confirmed holdings carry `institution_value` and securities carry `name` and `ticker_symbol` for a server-side join.
**Processing**: A spawned retrieval agent runs the three read-only Plaid commands. Snapshot finance sources ending in `_XXXX` are matched to account masks, preferring the same institution when available. Matched accounts receive current balances; credit and mortgage liabilities are normalized as negative net-worth values. `titan`, `titan_ira`, `wealthfront_saving`, `citi`, `usbank_cc`, `bonds`, and `fidelity_*` always retain snapshot values per the supplied contract. Holdings are joined to securities by the opaque IDs inside the action, then only ticker/name/value/share are persisted or returned; internal IDs and raw JSON are never exposed.

### Firance monthly snapshot files on the user's Mac
**Used by**: `refreshFinanceData` background retrieval -> `ingestFinanceData`; all monthly charts, monthly KPIs, FIRE calculations, and grouped account details
**Test command**: Source behavior was established from reads of the FinanceData directory (date-named files, one per snapshot); this builder seat has no direct device-file connector, so it will use the requested `ctx.agent.spawnTask` retrieval path at runtime.
**Sample output**: Historical files were re-read and verified after mortgage backfill; current files use three-line records containing `finance_source`, `type`, and `number`, while field order differs across years.
**Processing**: The retrieval agent lists files first, then reads all date-named files without writing to the Mac. The parser groups each three-line record and reads keys by name rather than position. Date filenames are parsed and sorted chronologically. Monthly rows are recomputed from source records using the exact Firance aggregation rules. If the Mac is unavailable or no valid files are returned, the action retains the last server-cached monthly dataset.

## Agent-task sources
### Weekly finance refresh
**Delivered by**: `refreshFinanceData` -> detached agent task -> `ingestFinanceData`
**Checked with**: The action contract will require the retrieval agent to list/read Firance files and run only `plaid accounts`, `plaid liabilities`, and `plaid investments-holdings`, then submit a strictly validated JSON payload to the save action. No browser work is required.

## F0.6 cashflow alignment (2026-10-18)
- Source contract extended additively per the current Firance cashflow rules (local Firance `cashflow.js` / `monthlyRecords.js` / `tests/cashflow.test.mjs` as referenced in the muse_life plans F0.6 entry): entry types `flexible_spend`, `cashflow_adjustment`, `investment_external_adjustment` are accepted, and per-record extended keys (`cashflow_role`, `balance_date`, `status`, investment period and verification metadata, plus any other key into `extra`) are preserved by key — the reader no longer assumes exactly three lines per record, never writes back to the source, and never backfills verification marks for history.
- Snapshot keys accept `YYYY-MM` (month-end valuation, normalized to the last day) and `YYYY-MM-DD`; a filename alone never proves transaction coverage. First-day (month_start) and mid-month snapshots are a different caliber from month-end and cannot be mixed into a back-calculation.
- Contribution resolves by field existence: an explicit `investment_contribution` of 0 never falls back to the legacy `transfer` alias; matching pairs are used once, conflicting pairs degrade to a 待核对 conflict state (standard value governs, provenance withheld).
- Flexible spend priority: recorded `flexible_spend` as-is (true 0 and negative net refunds preserved) → full-coverage Plaid transactions → the cash/credit-only identity `income + other net cashflow − investment cash transfer − fixed spend − Δ(cash + credit balances)` when consecutive month-end snapshots share classification, scope and fresh balance dates. Loan principal and HSA/bond (non-cash) changes are excluded by classification. Ineligible or negative back-calculations are stored as null with a named reason and the preserved difference — never clamped to 0.

## F1.6 investment performance reconciliation (2026-10-18)
- Source contract per the current Firance investment-performance rules (local Firance `investmentPerformance.js` / `tests/investmentPerformance.test.mjs` as referenced in the muse_life plans F1.6 entry): a month's investment return = ending balance of ALL `investment` snapshot entries − the previous snapshot's same-scope balance − the whole interval's external net flow. Net flow = the resolved cash contribution (F0.6 standard-field/alias resolution) + `investment_external_adjustment` (non-bank direct investment: RSU vesting, employer direct contributions; withdrawals negative). In-portfolio buys/sells, broker-to-broker transfers and retained dividends are not flow entries and are never double-counted.
- Degradations are explicit and stored per month (`investmentNetFlow`, `investmentReturnReason`, both additive with legacy defaults): the first snapshot is the period starting point (no return); a cross-month gap spans the whole interval and is not a monthly return (the missing month's flows are unknown); investment-account scope changes, explicitly unverified balances/flows, carried-over (stale) balance dates, and missing or conflicting contribution records each null the return with a named reason. Negative returns and net withdrawals keep their signs. The dashboard-level period figure accumulates only when every interval reconciles — it never bridges a blocked interval with 0. Balances derive only from snapshot `investment` entries: Plaid holdings detail never substitutes for or adds to account balances, and the weekly net-worth balance-difference fact card is never re-labelled as market return. Stored payloads are re-derived through the same gated reconciliation on read (`normalizeFireMetrics`), so legacy un-gated figures are not trusted; pre-metadata payloads degrade to a named 待核对 reason instead.
- Verification: `validate-investment-performance.mjs` (35 synthetic assertions against the real production functions: fixed case 100000→115000 with 10000 cash in → 5000; plus 3000 non-bank direct → 2000; withdrawal/negative-return sign preservation; first-period, explicit 0, missing, conflict, alias; unverified balance/flow; stale balance date; cross-month gap; scope add/remove; two-interval period coverage with a later gap breaking accumulation; legacy read-path re-derivation and scope-unknown degradation), alongside the existing cashflow / monthly-facts / facts-card / payload / color-vision suites.

## F1.1 available-cash emergency coverage (2026-10-18)

Only `cash` accounts enter the numerator — a positive balance alone never qualifies, and credit/debt balances never mix in. Account rows carry the classification and balance date additively (`cashflowRole` / `balanceDate` / `availableCash`, legacy defaults on read); original balances and the broader `deposits` net-worth fact are never rewritten.

The read path re-derives the summary from stored account rows (`ensureAvailableCash`) so legacy payloads get the same classified numerator without backfilling storage.

Fewer than 3 months, non-positive average spend, or missing/stale cash produce no coverage figure — the gap is stated, never 0-filled (a true cash 0 with a valid basis is a real 0 months).
- Owner account scope is an on-page trial only: the 可动用现金账户范围 panel lists every balance account with its text classification and balance date; unchecking cash accounts re-sums the selected original balances in the client for this view only — nothing is saved, sent to the server, or rewritten. Excluding every cash account yields no coverage figure.

## F0.6/F1.6/F1.1/F2.3 exact-binding rework (2026-10-18)
- F0.6 endpoint binding is now EXACT: in the cashflow back-calculation, a participating account's balance date must equal its own endpoint snapshot's actual date (a `YYYY-MM` balance date normalizes to that month's last day). A same-month older day, a future day, or an invalid calendar date (e.g. 09-31) at either endpoint degrades the estimate to null with a reason naming the endpoint, the account and the recorded date （沿用旧余额日期）. "Unverified" is consumed from both `verified === false` and the raw status strings `unverified` / `carried_forward_unverified`. The recorded-0 / net-refund priority, the 400-class estimates on exact dual-end matches, and the loan / non-cash exclusions are unchanged.
- F1.6 native flow fields are wired end to end: the refresh prompt requires `investment_period_start` / `investment_period_end` / `investment_flow_verified` to stay under their original keys in the record's `extra` (never merged into the generic period/verified fields; `status` returned verbatim). At ingest they are promoted verbatim into additive `entryMeta` fields `nativePeriodStart` / `nativePeriodEnd` / `nativeFlowVerified` (null defaults; legacy archives readable). The return gate uses the effective period (generic first, native as fallback; both present and different = named period conflict), treats native `investment_flow_verified=false` (or a contradiction with the generic flag) and balance-endpoint `status=carried_forward_unverified` as unverified/conflict, and binds investment balance dates exactly (same rule as F0.6). Period coverage is judged PER CHANNEL — cash (`investment_contribution`/`transfer`) vs non-bank direct (`investment_external_adjustment`): each channel's effective periods must cover (previous snapshot date, this snapshot date] without reaching outside it (crossing out makes the amount unattributable, whole record excluded); one channel never substitutes for another; a channel with dated records elsewhere (or carrying the native verification mark) degrades when its own records lack periods; a channel with neither periods nor the native mark keeps the legacy caliber, never re-labelled verified. A month whose flow proof fails reports `investmentNetFlow: null`, and any unproven interval nulls the whole-period `investmentPerformance.netFlow` (the card states 未知 with the per-interval pointer); proven intervals' monthly returns and recorded amounts stay readable.
- F1.1 legacy read path: account rows carry an additive `status` field (null default). `getDashboard`'s read path (`ensureAvailableCash`) fills a legacy row's missing `verified` / `status` / `balanceDate` from the latest month's preserved `entryMeta` by financeSource — only explicit preserved values; what the archive never kept stays missing — so an archive whose entryMeta preserved `verified=false` / `status=carried_forward_unverified` degrades available cash to null (named unverified) without a refresh. Staleness is exact equality with the snapshot date (future dates are gaps too).
- F2.3 legacy read path: `ensureHoldingsConsistency` moves a stored `holdingsCash` row whose ticker-declared currency conflicts with its currency field (e.g. CUR:USD + CAD) into `holdingsUnclassified` with 「现金币种冲突」 named, and rebuilds `cashPosition` from the retained cash rows (null when no USD row survives). Archives without `holdingsCash` keep the CUR:USD folding behavior; stored shares and concentration are never recomputed.
- Client period card is per-interval: one row per real endpoint pair (recorded cash amount, recorded non-bank amount, the interval's reconcilable net flow or —, its return or 待核对 reason); each flow record's coverage label is judged against its own interval （覆盖本区间 / 仅覆盖部分 / 跨出本区间 / 不在本区间内 / 未提供期间） with its effective period (generic ?? native) and native verification state shown as text; monthly records use the same effective period.
- Verification: the four affected suites were extended in place — `validate-cashflow.mjs` (79), `validate-investment-performance.mjs` (81), `validate-available-cash.mjs` (71), `validate-holdings.mjs` (66) — alongside monthly-facts (73), facts-card (85), payload (12) and color-vision (16): 483 synthetic assertions against the real production functions, all passing.

## F0.7 refresh generation binding + F1.6 period proof + F1.1 metadata association + F0.5/F0.7 status band (2026-10-18)
- F0.7 generation/CAS (migration 0003, additive columns `generation` / `claimed_generation` / `started_at` on `finance_state`): every refresh start mints a generation id, stored with the running state alongside the attempt start instant (`started_at`, distinct from the `updated_at` state-write instant); the spawn prompt requires the background task to echo that generation verbatim on BOTH the success and failure `ingestFinanceData` callbacks (the field is optional in the schema, so pre-generation callers stay schema-compatible). Spawn-tail write-backs go through a conditional update matching id + this generation + still `running`, so a spawn returning after its callback settled can never resurrect `running` over `idle`/`error`, and a stale spawn from a previous generation leaves the newer generation untouched (the refresh return is then honestly `already_running`, or "更新已完成" when its own generation's callback already settled it). Callbacks pass a pure generation gate (stored generation null = legacy row, ungated; a non-running state ignores every callback for its generation — a generation settles once) and a pure callback decision (failure eligible only while running, so a late failure never flips a settled success to error; a success whose `payload.asOf` is not newer than the stored snapshot is ignored, so the snapshot never regresses; a success stamped before the current refresh started is ignored). Eligible callbacks arbitrate through a claim: a conditional update stamping a fresh claim token against the exact read snapshot (updatedAt + status + generation + still unclaimed); the loser re-reads once and stops if a claim is already held. The settle (payload write included) is one conditional update bound to the claim token + generation; a superseded winner saves nothing and settles nothing. Identity is unchanged: finance actions remain strictly owner-checked; no viewer-less channel was added. Legacy rows and payloads keep working (ungated callbacks still subject to the asOf decision; migration 0003 leaves legacy rows with null generation/started_at and the dashboard renders that honestly).

Coverage is judged per channel AND per independent source: within a channel, different sources' periods never splice into one proof (source A covering the first half + source B the second half leaves the channel unproven, reason naming the source and the no-splicing rule); a record dated entirely outside the interval is excluded whole (reason states the amount is not mixed into this segment's net flow); records with only a period start, with no period at all, or pure legacy records with neither period nor verification mark no longer reconcile — the recorded facts stay readable but the segment's `investmentReturn` and `investmentNetFlow` are null and the period card shows 待核对. Normal controls (return 5000, RSU-inclusive 2000), explicit 0, withdrawals, negative returns, cross-month gaps, first period, native-field conflicts, dual channels each fully covered, and multi-month segments all keep their verified behavior.
- F1.1 metadata association: the `ensureAvailableCash` read-path fill now binds candidates to the SAME snapshot (the month whose key equals the payload's `sourceMonth`), the SAME type (cash-class `account` entries only — a same-named income or investment entry's `verified=true` can never fill a cash account row, and the account entry's own explicit `verified=false` is preserved so available cash stays null, named unverified), and unique associability per field: duplicate account metadata that agrees fills the field; conflicting duplicates leave it missing (conservative). The fill remains read-path only — the stored blob is never written back (verified byte-identical in tests).
- F0.5/F0.7 status band (client, read-only, after the access check): shows the last successful data date (`payload.asOf`), the current/last attempt start (`refresh.startedAt`), the state-write instant (`refresh.updatedAt`, labelled 状态写入时刻 — never called a heartbeat or a data date), a symbol + text status (↻ 正在更新 / ▲ 更新未成功 / ✓ 已同步， Okabe-Ito friendly, never color-only), and the next available action; while running the copy states explicitly 「正在更新，当前显示上次成功数据」 and that only a legal ingest save replaces it; error/stale states offer the retry action in text while the old cards stay on screen. Month-availability facts derive from the real months + integrity metadata only （上一完整月 已齐备/未核实/缺失 — never inferred complete from `asOf`; 当月仅进行中 with its snapshot date; unverified history months named). An expandable ledger reuses the F0.5 four source rows （本地月度记录 / 银行余额 / 交易 / 持仓）, each with its source data date, obtained range and this-run result: while running the result reads 尚未落盘 (a background completion without a legal ingest save is never labelled 数据已更新）, a failed attempt reads 未写入新数据、保留上次成功数据， and stages the platform does not timestamp （交易） honestly read 「未知」 — no fabricated percentages or task-completion claims.

## F-ARCH-001·SAVE-1 concurrency arbitration + caliber labeling (2026-10-24)
- SAVE-1 P0 fix (PM review 2026-10-24 13:12 PDT): the arch ingest append is now ONE conditional `INSERT INTO arch_net_worth ... SELECT ... WHERE NOT EXISTS (SELECT 1 ... WHERE pulled_at >= ? AND json_valid(payload)) RETURNING id` — the database evaluates the guard at commit time, so two concurrent same-version calls can no longer both pass the handler's read-check and both append. Exactly one lands; the loser re-reads the committed rows and is classified under the existing sequential rules (equivalent content → reuse the winner's row id and succeed idempotently; different content → typed `version_conflict`; overtaken by a newer version → `stale_version`). Cross-version races can never regress the current figure (selection stays greatest pulledAt, ties greatest id). Deliberately NO unique index / migration: a unique constraint on `pulled_at` could not build over, or would force deleting, same-version duplicates the pre-fix race may already have stored — all history is preserved verbatim, the change is code-only and rollback loses no data. ## Long-term data behavior- **Refresh policy**: One silent weekly artifact-action schedule dispatches `refreshFinanceData`. First build also invokes it once for real initial population. The page reads the latest cached snapshot immediately; no client-side Plaid or Mac access occurs.
- **Growth**: Persist one bounded current snapshot containing full monthly aggregates/source rows, latest live fusion, holdings, and account details, plus the previous successful weekly live net worth needed for week-over-week delta. Replace the current snapshot atomically rather than appending unbounded raw Plaid history.
- **Ordering**: Monthly series sort by the date key ascending for chart math; headline values use the newest two monthly rows. Accounts group by type and then sort by absolute value descending. Holdings sort by market value descending; the first 10 form the summary and the full normalized set is persisted for the read-only explorer (F2.3).
- **Time semantics**: `asOf` is the successful refresh instant; source month keys remain calendar dates from Firance. Failed refreshes preserve all prior values and set a visible stale/failure status without altering the prior successful `asOf`.

## Rejected approaches
- **Tried**: Treating Plaid as the sole source of truth.
  **Why rejected**: The supplied contract names several non-Plaid accounts and all monthly income/spend/contribution history as Firance-only; dropping them would understate net worth and break the requested 1:1 logic.
- **Tried**: Reading Firance keys by fixed line order.
  **Why rejected**: Historical files use different key ordering, so parsing by position would silently corrupt rows.
- **Tried**: Fetching live data directly from the browser.
  **Why rejected**: The data is account-gated and scheduled; it belongs in validated server actions with cached fallback.
- **Tried**: Fabricating an initial dashboard when sources are unavailable.
  **Why rejected**: The artifact must show only real user finance data; until the first successful refresh it will show an honest empty/retry state.
