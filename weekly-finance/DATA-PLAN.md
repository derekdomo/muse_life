## Tested sources
### Plaid linked financial data
**Used by**: `refreshFinanceData` background retrieval, live net-worth fusion, weekly comparison, holdings Top 10, account-detail refresh
**Test command**: `which plaid; plaid status | jq ...; plaid accounts | jq ...; plaid liabilities | jq ...; plaid investments-holdings | jq ...`
**Sample output**: Plaid is connected. The account read returned linked loan, depository, credit, brokerage, IRA, 401(k), HSA, and crypto accounts with masked suffixes and current balances. The liabilities read returned a mortgage at 2.375%. The holdings read returned 5 institutions and 72 holdings; a schema check confirmed holdings carry `institution_value` and securities carry `name` and `ticker_symbol` for a server-side join.
**Processing**: A spawned retrieval agent runs the three read-only Plaid commands. Snapshot finance sources ending in `_XXXX` are matched to account masks, preferring the same institution when available. Matched accounts receive current balances; credit and mortgage liabilities are normalized as negative net-worth values. `titan`, `titan_ira`, `wealthfront_saving`, `citi`, `usbank_cc`, `bonds`, and `fidelity_*` always retain snapshot values per the supplied contract. Holdings are joined to securities by the opaque IDs inside the action, then only ticker/name/value/share are persisted or returned; internal IDs and raw JSON are never exposed.

### Firance monthly snapshot files on the user's Mac
**Used by**: `refreshFinanceData` background retrieval -> `ingestFinanceData`; all monthly charts, monthly KPIs, FIRE calculations, and grouped account details
**Test command**: Source behavior was established from reads of the FinanceData directory (date-named files, one per snapshot); this builder seat has no direct device-file connector, so it will use the requested `ctx.agent.spawnTask` retrieval path at runtime.
**Sample output**: Historical files were re-read and verified after mortgage backfill; current files use three-line records containing `finance_source`, `type`, and `number`, while field order differs across years.
**Processing**: The retrieval agent lists files first, then reads all date-named files without writing to the Mac. The parser groups each three-line record and reads keys by name rather than position. Date filenames are parsed and sorted chronologically. Monthly rows are recomputed from source records using the exact Firance aggregation rules. If the Mac is unavailable or no valid files are returned, the action retains the last server-cached monthly dataset.

## F0.6 cashflow alignment (2026-10-18)
- Source contract extended additively per the current Firance cashflow rules (local Firance `cashflow.js` / `monthlyRecords.js` / `tests/cashflow.test.mjs` as referenced in the muse_life plans F0.6 entry): entry types `flexible_spend`, `cashflow_adjustment`, `investment_external_adjustment` are accepted, and per-record extended keys (`cashflow_role`, `balance_date`, `status`, investment period and verification metadata, plus any other key into `extra`) are preserved by key — the reader no longer assumes exactly three lines per record, never writes back to the source, and never backfills verification marks for history.
- Snapshot keys accept `YYYY-MM` (month-end valuation, normalized to the last day) and `YYYY-MM-DD`; a filename alone never proves transaction coverage. First-day (month_start) and mid-month snapshots are a different caliber from month-end and cannot be mixed into a back-calculation.
- Contribution resolves by field existence: an explicit `investment_contribution` of 0 never falls back to the legacy `transfer` alias; matching pairs are used once, conflicting pairs degrade to a 待核对 conflict state (standard value governs, provenance withheld).
- Flexible spend priority: recorded `flexible_spend` as-is (true 0 and negative net refunds preserved) → full-coverage Plaid transactions → the cash/credit-only identity `income + other net cashflow − investment cash transfer − fixed spend − Δ(cash + credit balances)` when consecutive month-end snapshots share classification, scope and fresh balance dates. Loan principal and HSA/bond (non-cash) changes are excluded by classification. Ineligible or negative back-calculations are stored as null with a named reason and the preserved difference — never clamped to 0.
- Verification: `validate-cashflow.mjs` (60 synthetic assertions against the real production functions, incl. the plan's fixed case cash 1000→1200 / loan −10000→−9500 / income 1000 / fixed 300 / contribution 100 → 400, explicit-0, recorded 0/refund, card repayment, HSA, gaps, renames, stale balances, invalid amounts, extended-field round-trip and legacy payload reads), alongside the existing monthly-facts / facts-card / payload / color-vision suites.

## F1.6 investment performance reconciliation (2026-10-18)
- Source contract per the current Firance investment-performance rules (local Firance `investmentPerformance.js` / `tests/investmentPerformance.test.mjs` as referenced in the muse_life plans F1.6 entry): a month's investment return = ending balance of ALL `investment` snapshot entries − the previous snapshot's same-scope balance − the whole interval's external net flow. Net flow = the resolved cash contribution (F0.6 standard-field/alias resolution) + `investment_external_adjustment` (non-bank direct investment: RSU vesting, employer direct contributions; withdrawals negative). In-portfolio buys/sells, broker-to-broker transfers and retained dividends are not flow entries and are never double-counted.
- Degradations are explicit and stored per month (`investmentNetFlow`, `investmentReturnReason`, both additive with legacy defaults): the first snapshot is the period starting point (no return); a cross-month gap spans the whole interval and is not a monthly return (the missing month's flows are unknown); investment-account scope changes, explicitly unverified balances/flows, carried-over (stale) balance dates, and missing or conflicting contribution records each null the return with a named reason. Negative returns and net withdrawals keep their signs. The dashboard-level period figure accumulates only when every interval reconciles — it never bridges a blocked interval with 0. Balances derive only from snapshot `investment` entries: Plaid holdings detail never substitutes for or adds to account balances, and the weekly net-worth balance-difference fact card is never re-labelled as market return. Stored payloads are re-derived through the same gated reconciliation on read (`normalizeFireMetrics`), so legacy un-gated figures are not trusted; pre-metadata payloads degrade to a named 待核对 reason instead.
- Verification: `validate-investment-performance.mjs` (35 synthetic assertions against the real production functions: fixed case 100000→115000 with 10000 cash in → 5000; plus 3000 non-bank direct → 2000; withdrawal/negative-return sign preservation; first-period, explicit 0, missing, conflict, alias; unverified balance/flow; stale balance date; cross-month gap; scope add/remove; two-interval period coverage with a later gap breaking accumulation; legacy read-path re-derivation and scope-unknown degradation), alongside the existing cashflow / monthly-facts / facts-card / payload / color-vision suites.

## F1.1 available-cash emergency coverage (2026-10-18)
- Emergency coverage numerator is 可动用现金 only, per the Firance `getCashflowRole()` classification (muse_life plans F1.1 supplement): an explicit `cashflow_role` wins; the name-based fallback classifies HSA, bond/treasury and retirement (IRA / 401k / 403b / Roth / pension) balances as `non_cash`, mortgage/loan as `debt`, credit cards as `credit`, and other account balances as `cash` when positive. Only `cash` accounts enter the numerator — a positive balance alone never qualifies, and credit/debt balances never mix in. Account rows carry the classification and balance date additively (`cashflowRole` / `balanceDate` / `availableCash`, legacy defaults on read); original balances and the broader `deposits` net-worth fact are never rewritten.
- Server summary (`live.availableCash` + stale sources + cash-account count) shares F0.5's per-source balance dates — no second source ledger: no cash account, or a cash account whose explicit balance date predates the source month, yields null (missing/stale cash never becomes a fabricated coverage figure); a true cash 0 stays 0. The read path re-derives the summary from stored account rows (`ensureAvailableCash`) so legacy payloads get the same classified numerator without backfilling storage.
- Denominator unchanged: the last 3 valid complete months with proven, non-anomalous spend (F0.4/F0.6 basis); the coverage note names the months used and the spend estimate. Fewer than 3 months, non-positive average spend, or missing/stale cash produce no coverage figure — the gap is stated, never 0-filled (a true cash 0 with a valid basis is a real 0 months).
- Owner account scope is an on-page trial only: the 可动用现金账户范围 panel lists every balance account with its text classification and balance date; unchecking cash accounts re-sums the selected original balances in the client for this view only — nothing is saved, sent to the server, or rewritten. Excluding every cash account yields no coverage figure.
- Verification: `validate-available-cash.mjs` (synthetic assertions against the real production functions: classification coverage incl. retirement/HSA/bonds/credit/debt, end-to-end numerator vs unchanged deposits/net-worth facts, unrewritten balances, true 0 / missing / stale / fresh dates, YYYY-MM month-end normalization, legacy read-path re-derivation, denominator last-3 with named months, client default/trial/exclude-all/stale-excluded coverage), alongside the existing cashflow / investment-performance / monthly-facts / facts-card / payload / color-vision suites.

## F2.3 full holdings explorer (2026-10-18)
- The payload now persists a bounded FULL normalized holdings set alongside the Top 10 summary (muse_life plans F2.3 supplement, referencing local Firance `portfolioAnalysis.js` / `Portfolio.jsx` as the model): same ticker merged across accounts with the holding institutions kept on the merged row as an explainable fact; the refresh agent is instructed to return every holding (no pre-truncation) with its `iso_currency_code` and institution, a missing `institution_value` as `value: null`, and negatives as-is.
- The concentration denominator is FIXED at ingest: `holdingsTotal` = the sum of every valid non-cash holding (positive, known-USD), long tail included; every stored share and the Top-3 concentration divide by it. The read path (`ensureHoldingsConsistency`) preserves stored shares/concentration exactly and only folds an ancient in-list CUR:USD row into the separate cash — it never recomputes from the stored Top 10. Client search filters visible rows only and cannot move the denominator.
- Cash is listed separately, one row per cash ticker/currency (`holdingsCash`); only CUR:USD sums into the legacy `cashPosition` total. Rows that cannot enter the USD denominator — missing market value, negative or zero position, unknown currency, non-USD currency — are preserved as `holdingsUnclassified` （待核对） with a named reason, never dropped and never defaulted to USD positive holdings. The stored full set is bounded at 500 merged tickers (largest kept, `holdingsTruncated` flagged; the denominator still covers every valid holding).
- Legacy payloads written before this change carry only the Top 10 (`holdingsComplete=false` by schema default): their stored shares/concentration keep the ingest-time full-set denominator, the long tail is stated in the UI as unrecoverable until the next successful refresh, and no full denominator is ever recomputed from the Top 10. Holdings detail is a Plaid market-value caliber and is never added to investment account balances or fed into the F1.6 reconciliation. The explorer is read-only: no trading, recommendations, prediction or backtesting.
- Verification: `validate-holdings.mjs` (synthetic assertions against the real production functions: 12-holding long tail with full-denominator shares/concentration, cross-account ticker merge with institution union, CUR:USD + CUR:EUR cash separation, missing-price / negative / zero / non-USD / unknown-currency classification, empty and cash-only inputs, 501-row bound with whole denominator, legacy + ancient read-path preservation, client filter purity, and source wiring), alongside the existing cashflow / investment-performance / available-cash / monthly-facts / facts-card / payload / color-vision suites.

## Long-term data behavior
- **Refresh policy**: One silent weekly artifact-action schedule dispatches `refreshFinanceData`. First build also invokes it once for real initial population. The page reads the latest cached snapshot immediately; no client-side Plaid or Mac access occurs.
- **Growth**: Persist one bounded current snapshot containing full monthly aggregates/source rows, latest live fusion, holdings, and account details, plus the previous successful weekly live net worth needed for week-over-week delta. Replace the current snapshot atomically rather than appending unbounded raw Plaid history.
- **Ordering**: Monthly series sort by the date key ascending for chart math; headline values use the newest two monthly rows. Accounts group by type and then sort by absolute value descending. Holdings sort by market value descending; the first 10 form the summary and the full normalized set is persisted for the read-only explorer (F2.3).
- **Time semantics**: `asOf` is the successful refresh instant; source month keys remain calendar dates from Firance. Failed refreshes preserve all prior values and set a visible stale/failure status without altering the prior successful `asOf`.

## Image plan
Imagery not needed: this is a private numeric finance dashboard whose visual subjects are deterministic charts, progress bars, and account rows; decorative or generated imagery would compete with the core financial reading task.

## Rejected approaches
- **Tried**: Treating Plaid as the sole source of truth.
  **Why rejected**: The supplied contract names several non-Plaid accounts and all monthly income/spend/contribution history as Firance-only; dropping them would understate net worth and break the requested 1:1 logic.
- **Tried**: Reading Firance keys by fixed line order.
  **Why rejected**: Historical files use different key ordering, so parsing by position would silently corrupt rows.
- **Tried**: Fetching live data directly from the browser.
  **Why rejected**: The data is account-gated and scheduled; it belongs in validated server actions with cached fallback.
- **Tried**: Fabricating an initial dashboard when sources are unavailable.
  **Why rejected**: The artifact must show only real user finance data; until the first successful refresh it will show an honest empty/retry state.
