### 1.2 属性/装备加成（仅作用于 steps/sleep/strength/quest_steps 四域）

- 属性映射：力量→strength、耐力→steps、精神→sleep、体力→quest_steps。
- 属性部分：`min(50%, 2% × 该属性点数)`（每点 +2%，每域封顶 +50%）。
- 装备部分：已装备物品中同域 pct 直接相加（无封顶常数，目录 pct 见 §1.5），叠加在属性部分之上。
- 最终 XP：`floor(基础XP × (1 + (属性% + 装备%) / 100))`。
- 时序（2026-10-20 更正，PM 00:27 实证，原表述作废）：此前「加成只作用于分点/装备之后新入账」与线上实际不符。实际行为按来源状态分四种：(a) 同一来源引用（sourceUpdatedAt 未变）重开 → skip，零变化，加成不重估；(b) 来源版本前进（sourceUpdatedAt 变化）但事实值相同 → 候选按**当前**属性/装备加成重算，账本行走 revise 并按差量调整金币——即分点/买装备后，过去日期的同版（v2）行会在下一次来源版本前进时被新加成追溯重估（实证：某过去完整日步数 20,000 不变，首次候选 20 XP；其后耐力 25 点＋疾风短刃使候选变为 33，revise 的 goldDelta=+13）；(c) 来源事实真实上调/下调 → 同 (b)，按当前加成重算候选并修订差量；(d) 规则版本升级 → 旧版本行（v1）skip，永不重算。用户影响：购买/分点后历史奖励可能跳变，页面解释须按本口径，不得再称「只作用于新入账」。
- 待定案提案（未实施、未混入线上）：保守方案为首次结算时把该行所用加成版本/数值绑入账本行，事实修订沿用原加成重算、只有新日期行用新加成；旧行无法恢复原加成的标「加成未知」并保旧值、不批量重算。此方案会改变已批准经济参数的实际效果，须所有者核对差异后拍板，实施前线上维持上表实际行为并如实标注。（需用户确认）

### 1.3 属性点与等级（现行过渡 XP 等级，LEVEL 定案后替换）

- 等级：`floor(累计XP / 100) + 1`（GAME_XP_PER_LEVEL=100）。
- 属性点：`attrPointsEarned = (等级 − 1) × 3`，只增不减（单调抬升）；未分配 = 已得 − 已分配（四属性之和），下限 0。
- 分点动作 `allocateAttribute`（严格 owner，单次 1–50 点）。

### 1.4 金币

- 初始化：首次 S2 读取时余额 = 当时累计 XP（一次性换算，goldInitialized 标记）。
- 铸造：此后每笔 XP 结算按实际入账 XP 1:1 铸金币；修订差量时金币按 goldDelta 跟随（下限 0）；装备 domain=gold 的 pct 放大铸造（皮甲 +10%）。
- 每日任务：每项平额 15 XP + 40 金币，共 3 项——steps_10000（今日步数 ≥10,000）、strength_1（今日完成力量训练 1 次）、sleep_7h30（今晨主睡眠 ≥7.5h）。

### 1.6 修订差量（CWEB-SETTLE-001，与 §1.1 同版生效）

同规则版本、来源 sourceUpdatedAt 变化且候选值不同 → 原地修订（xp/gold/来源引用一次 UPDATE），总额以账本 SUM 自然移动；同引用重开零变化；值已相等只刷新来源引用；旧规则版本行 skip 永不重算；从不删行、不回收已解锁内容。口径澄清（2026-10-20，PM 00:27）：此处的「一次 UPDATE」只覆盖单个账本行本身，不等于账本行＋金币余额＋profile 的跨对象原子性；跨对象一致性属 CWEB-SETTLE-001／CWEB-PROFILE-SAFE-001 的 P0 修复范围，不能以本节表述宣称该 P0 已关闭。另注：来源版本前进但候选的**事实值**相同时，若当前加成已变，候选 xp 仍会因加成重算而不同并触发 revise（见 §1.2 (b)），「候选值不同」包含这种纯加成变化。

### 1.7 合成边界核算（固定 synthetic，非真实数据）

- 步数 0 → 0 XP（真实 0，非缺失）；999 → 0；1000 → 1；19,999 → 19；20,000 → 20；45,000 → 20（封顶）。
- 睡眠 0h → 0；3.5h → 5；6.99h → 9；7h → 10；9h → 10。
- 加成：基础 20 XP、属性 25 点（+50% 封顶）＋同域装备 +15% → floor(20×1.65)=33；属性 30 点仍 +50%（封顶生效 → 同上 33）。
- 金币：修订使某行 XP 20→5 时 goldDelta=−15，余额下限 0，不出现负余额。
- 任务：同一任务同日第二次达标判定 → 已入账，零重复发放（(local_date, daily_task, task_id) 主键）。

## 3. CWEB-MVP-001·S3：设计/接口（首片目标 2026-10-22）

- 范围：所有者自设个人奖励清单（名称＋所需金币），金币达标后兑换，兑换与 S2 同一金币账本：兑换 = 一笔负向金币流水（新类别 `reward_redeem`，detail=奖励 id），余额由账本与 profile 一致校验，禁止透支（余额不足 typed 拒绝、零写入）。
- 原子性：兑换的余额扣减与回执行写入同一原子操作；重复提交同 idempotency 键返回 already_resolved 回执，不重复扣账（沿 W-PLAN/CWEB-SETTLE 的认领模式）。
- 接口（拟）：`getGameState` 响应加 `rewards[]`（id/名称/价格/状态：可兑换|金币不足|已兑换次数）与 `redemptions[]` 回执（奖励名/金额/时间）；新动作 `saveReward`（owner，增改自设奖励）、`redeemReward`（owner，入参 reward_id + expected_balance_version 防旧确认认领新余额）。
- 页面：角色页奖励区列「下一可获得的自设奖励」（承接 CWEB 首屏口径），兑换成功给回执行，不引入商店随机/抽卡/真实付费。
- 依赖：S2 金币余额已可用（已满足）；不依赖 LEVEL/境界。旧账本不重算、不回写。

### 4.2 固定 synthetic 对账（逻辑层，非年龄年数）

- 全空输入 → 输出「当前未能评估」，境界显示上次值＋日期并标旧，不降阶、不奖励。
- partial 输入 → 同上（预览），不入账本、不改境界。
- 同输入重复打开 → 幂等，境界与修为零变化。
- 迟到修订（同来源版本内数值变差）→ 按当前模型重算一次，允许降阶；修为累计与已兑回执不删。
- 来源变好 → 升阶呈现为「突破」事件，仅首次有效结算触发，重复打开不重复播。
- 年龄段切换/生日/LA 跨日 → 以 LA 本地日与来源日期为准；年龄差曲线分别画「实际年龄（来源日期）」与「模型值（来源日期）」两条，不用旧快照逐年自动 +1 冒充改善。

### 4.4 可运行离线候选实跑（实现方 2026-10-20 补充，路径 A）

`health-dashboard/validate-level-candidate.mjs`（纯 Node、零依赖、仅 synthetic 输入）把 §4.1/§4.2 的逻辑矩阵落成可执行候选，2026-10-20 本地实跑 **16/16 通过**（退出码 0）：

- 候选定义：五信号（静息心率/HRV/主睡眠/步数/力量周次）各自对个人 28 日基线作方向调整 z 分（钳制 ±2.5），等权平均后 `index = clamp(50 + 10·meanZ, 0, 100)`；可用信号少于 3 个、partial 或全空 → 「当前未能评估」，不产生指数、不动境界（与 §4.2 一致）。
- 固定 synthetic 结果：基线日 index=50；优于基线日 62.8；差于基线日 35.4（严格浮动成立：指数可跌）；重复评估幂等；缺失信号重归一化不当 0；极端值钳制在 0–100。
- 境界阶梯结构：10 境界 × 4 小阶 = 40 阶，阈值单调无缺口；年龄段校准以提案乘数（40s 1.00 / 50s 0.92 / 60s 0.84 / 70+ 0.76）降低同阶门槛——同 index 在 60s 段达到不低于 40s 段的阶位，实跑断言通过。
- **敏感性观察（如实记录，属待定案）**：现提案阈值表（第 k 阶要求 `20 + 2k·年龄段乘数`）下，基线日 index=50 即落在第 15 阶（金丹·圆满），优/差日仅 ±6 阶——锚点偏高、中段压缩。替代锚法（如地板抬高到 35、或按 index 分位映射）未定案，不擅改；此观察正是离线候选要暴露的问题，不构成线上参数。
